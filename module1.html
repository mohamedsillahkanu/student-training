read_lines()readr

read lines

What it is

Reads a file as plain text, one line of the file per element, and parses nothing. No columns, no types, no header — just the characters that are actually in the file.

When to use it

Before you read any file you have not seen before, and the moment a read gives you something strange: one very wide column, a header made of nonsense, a row count that is one too many. Thirty seconds here saves an hour of guessing.

how to write itread_lines("file", n_max, skip)
More on this one

Every other reader in this module makes a decision for you: where the header is, what separates the fields, what type each column should be. read_lines() makes none of them, which is exactly why it is the right first move on an unfamiliar file. Three things are visible in the output and nowhere else. First, the separator: a \t means tab, a semicolon means read_csv2(), and if the fields run together with no separator at all you need read_fwf(). Second, the junk on top: title lines, a generation timestamp, a blank line — count them and that is your skip. Third, the encoding: names that print as Bo<U+00A0>District tell you to reach for locale() before you blame the data. Two habits worth keeping: always pass n_max so you do not pull a two-million-line file into memory to look at the top of it, and always run tail() on the lines as well as the head, because exports put their surprises at the bottom where nobody looks.

What is really happening

R keeps no link to the file after the read. You get a copy in memory with a name you chose, and the file on disk stays exactly as it was — so nothing you do in R can damage the original data.

The pattern behind every read

Always the same three parts: object <- reader("file"). Check where R is looking with getwd(), check the file is there with file.exists(), then read it.

What happensillustration

Nothing happens until the data is inside R

R does not open files the way Excel does. Nothing appears on screen when you read a file, and there is no window showing the spreadsheet. What happens instead is that R copies the contents of the file into your session and gives that copy a name. From then on you work with the name, not the file. The file on disk is never changed by anything you do, which is exactly why this way of working is safe: you can make a mistake in your code fifty times and the original data is still untouched.

Every read has the same three parts

A name for the result, the arrow, and a function that matches the format: cases <- read_csv("routine_cases_dummy.csv"). That is the whole pattern. The eight cards after this one change only the middle part — read_csv() becomes read_excel(), read_dta() or read_sav() depending on what you were sent. Learn the pattern once and every new format is a ten-minute job rather than a new skill.

Why we spend a whole week on it

In routine malaria work the data arrives in whatever format the sender happened to use: a DHIS2 download as .csv, a supervision checklist as .xlsx, an MIS extract as .dta or .sav, chiefdom boundaries as .geojson. If reading a file is a struggle, you end up re-typing numbers into a spreadsheet by hand, and every figure in your report becomes something nobody can check. If reading is routine, your whole analysis is a script that anyone can run again next month and get the same answer.

The readers live in packages

Base R can read a plain .csv on its own, but everything else needs a package: readr for text files, readxl for Excel, haven for Stata and SPSS, sf for maps. Getting a package ready is two jobs, not one — install.packages("readr") downloads it onto the computer once, and library(readr) switches it on in the session you are working in now. You install once and load every time. The pacman package folds the two into a single p_load() call, which is what most of this course uses, but you should recognise both because nearly all the R code you meet online is written with library().

Changing the folder, and the habit that saves you

You move R with setwd("path") and you check where you are with getwd(). Relative paths do the work: setwd("data") steps into a subfolder, setwd("..") steps back up, and setwd("../shared") goes up and across. Both are worth knowing because you will use them in the console constantly.

What you should not do is leave setwd("C:/Users/mohamed/Documents/r-training") at the top of a script. That line works on exactly one computer, and it is the single commonest reason a shared R script fails on a colleague's machine. Three better habits, in order: open the folder as an RStudio project so the working directory is set for you; keep your paths relative, as in read_csv("data/routine_cases_dummy.csv"); or use here::here("data", "file.csv"), which finds the project root wherever the project has been copied to.

Two things cause almost every failure

The first is the working directory: R looks for the file in one particular folder, and if the file is somewhere else you get Error: 'routine_cases_dummy.csv' does not exist. The second is using the wrong function for the format, which either errors or, worse, succeeds and gives you nonsense. The five examples below deal with the first problem, and the eight cards after this one deal with the second.

1bounds <- readOGR("chiefdoms_sl.geojson")bounds <- st_read("chiefdoms_sl.geojson")readOGR() is from the retired rgdal package. st_read() from sf replaces it.
2bounds <- fromJSON("chiefdoms_sl.geojson")bounds <- st_read("chiefdoms_sl.geojson")A .geojson file is JSON, so this reads something — but the geometry is lost and you cannot draw a map from it.
3bounds_shp <- st_read("chiefdoms_sl.dbf")bounds_shp <- st_read("chiefdoms_sl.shp")Point st_read() at the .shp. The .dbf holds the attributes and is read automatically.
4bounds_shp <- st_read("chiefdoms_sl")bounds_shp <- st_read("chiefdoms_sl.shp")Give the file name with its extension, or sf treats the string as a data source name and errors.
5st_bbox(bounds)st_crs(bounds)st_bbox() gives the bounding box — the extent, not the coordinate system.
6proj4string(bounds)st_crs(bounds)proj4string() belongs to the old sp package.
7select(bounds, -geometry)st_drop_geometry(bounds)The geometry column is sticky: select(-geometry) does not remove it from an sf object.
8as.data.frame(bounds)st_drop_geometry(bounds)That drops the sf class but keeps the geometry column, so the table is still full of coordinates.
